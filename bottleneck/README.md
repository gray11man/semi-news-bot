# 산업변화 레이더 — 기존 뉴스 봇 전면 교체본

이 봇은 “무슨 뉴스가 큰가” 대신 **다른 산업의 변화가 어디에 새 수요를 만들고, 그 수요 때문에 누가 가격 결정력을 얻는가**를 탐색합니다. 초기 단서는 가설로 보관하고, 원문과 과거 기록을 다시 찾아 검증합니다.

예를 들어 “전력 공급·품질 요구 변화 → 저장장치·자가발전·전력기기”, “발전원 구성·설치비 변화 → 태양광·인버터·계통 접속”, “데이터 이동 방식 변화 → 광통신·스위치·통신망” 같은 연결을 찾습니다. **이 예들은 탐색 방법이며 현재 해당 산업의 수혜를 검증한 결론은 아닙니다.** AI와 무관한 인구·정책·원가·환경·공급자 퇴출·소비행태 변화도 같은 방식으로 조사합니다.

## 지금 완료된 것과 실행 상태

교체용 소스코드·설치 파일·테스트가 포함되어 있습니다. 기존 첨부 코드의 뉴스 선별 로직을 사용하지 않는 독립 프로젝트입니다. 기존 Gemini/Telegram 환경변수 이름은 유지했습니다.

사용자 PC나 기존 서버·GitHub 저장소에는 연결되어 있지 않습니다. **기존 예약 작업을 중단하거나 운영 중인 봇을 삭제한 상태가 아닙니다.** 실제 키를 받지 않았으므로 유료 Gemini 호출과 실제 Telegram 발송은 수행하지 않았습니다. 외부 RSS 실접속은 제작 환경의 네트워크에서 실패하여 실제 데이터 수집·URL 해독·모델 호출의 종단 검증은 남아 있습니다. 원문 접근 실패를 뉴스 없음으로 표시하지 않도록 구현했습니다.

## Windows에서 교체하기

1. 기존 봇의 작업 스케줄러/실행창을 먼저 중지하세요. 기존 폴더는 백업한 뒤 이 ZIP을 **새 폴더에** 풀어 주세요. 구버전 파일을 섞을 필요가 없습니다.
2. Python 3.10 이상이 설치된 PC에서 `install_windows.bat`을 실행하세요. 가상환경과 필수 패키지를 설치하고 테스트합니다.
3. 생성된 `.env`에 기존 `GEMINI_KEY`, `BOTTLENECK_TOKEN`, `BOTTLENECK_CHAT_ID` 값을 복사하세요. `PICK_MODEL`도 지원하며 새 `RADAR_MODEL`이 있으면 우선합니다.
4. `run_preview.bat`으로 미리보기를 실행하세요. 웹 수집과 Gemini 호출은 실제 수행하므로 API 사용량이 발생합니다. Telegram 발송과 실제 분석 기억은 변경하지 않습니다. `data/preview.md`에서 결과·오류·미처리량을 확인하세요.
5. 정상 확인 후 `run_bot.bat`을 실행하세요. 분석 기억을 저장하고 설정된 Telegram 채팅에 전송합니다. 기존 버전에서 업데이트할 때 `data` 폴더와 `.env`는 보존하고 소스 파일을 교체하세요. 새 예산 기본값은 환경변수를 추가하지 않아도 적용되지만, 기존 `.env`의 `DOCS_PER_THEME=20`은 직접 16으로 바꿔야 같은 기본 입력량이 됩니다.
6. 자동 실행하려면 기존 예약 작업의 실행 대상을 새 `run_bot.bat` 경로로 바꾸세요. 주기는 사용자가 정합니다. 이 패키지는 예약 작업을 자동 생성하거나 변경하지 않습니다.

기존 코드와 새 코드를 동시에 실행하지 마세요. 새 봇은 구버전 `seen_ideas.json`을 읽지 않습니다. 새 `data/radar.sqlite3`가 가설·원문·검증·알림 기억입니다. **반복 실행할 때 이 파일을 지우면 안 됩니다.**

## Linux 또는 직접 실행

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
cp .env.example .env
# .env에 기존 키와 채팅 ID를 입력한 뒤
.venv/bin/python main.py                 # 미리보기
.venv/bin/python main.py --send          # 기억 저장 + 전송
.venv/bin/python main.py --bootstrap --send  # 첫 실행에서 최근 30일 단서 수집
```

`--bootstrap`은 배경 수집 범위만 넓힙니다. 오래된 사건을 새 산업변화라고 알리지 않습니다. Google News RSS가 실제로 반환하는 결과 범위에 제한되므로 30일 전체 뉴스의 완전 수집을 뜻하지 않습니다.

GitHub Actions용 교체 패키지에는 기억 복원·저장 워크플로와 `ci_state.py`가 포함되어 있습니다. 압축본 최상위의 `GITHUB_SETUP.md`를 따르세요. 기존 PC용 구성도 동작합니다. Actions에서는 `bottleneck/state/`의 압축 DB를 임시 실행 디렉터리에 복원하고, 실행 후 다시 저장합니다.

## 동작 원리

RSS에서 최근 단서를 수집 → Gemini가 산업간 인과관계 가설과 후속 검색어를 작성 → SQLite에 후보와 원문을 보관 → 과거 365일 범위에서 가설·반증을 재검색 → 원문을 직접 읽고 근거 문장을 연결 → 별도 Gemini 호출로 숫자·발생일·원출처·서술을 재심사 → 코드가 알림 조건을 최종 판정합니다.

이 구조가 검색한 근거와 저장된 기억을 모델에 넣는 RAG입니다. 모델 내부 기억만으로 최신 사실을 만들지 않습니다. 장기 기억은 SQLite의 가설 목록·원문·근거·평가 이력이며 전송한 기사 제목 목록과 다릅니다.

## 알림 등급

| 상태 | 의미 |
|---|---|
| 관찰 | 새로운 연결 가능성은 있으나 원문·독립 출처·최근 변화 근거가 부족합니다. 보고서에 보관하며 기본 Telegram 알림은 하지 않습니다. |
| 초기 신호 | 독립 출처 추정 5곳 이상, 두 차례 심사에서 공식 원자료로 판단된 원문 1개 이상, 서로 다른 증거 축 2개 이상과 최근 사건 근거가 있습니다. 구조 변화의 **후보**입니다. |
| 변화 강화 | 초기 신호 조건에 더해 3개 이상의 증거 축, 실제 계약·집행 투자 근거, 3개 이상의 구별되는 사실이 연결됩니다. |
| 반증 경고 | 가설을 깨는 근거가 5개 이상의 독립 출처에서 나타나고 재심사를 통과합니다. 긍정 근거와 별도로 반증 출처를 집계합니다. |

5개 출처는 **산업 연결고리 전체를 뒷받침하는 출처 수**입니다. 개별 숫자·문장마다 동일한 주장을 5개 사이트에서 확인했다는 뜻이 아닙니다. 같은 보도자료의 재배포, 같은 통신사의 전재, 같은 출판사, 동일한 복사 본문은 중복으로 묶습니다. 원출처 식별에는 두 차례 모델 판단이 들어가므로 완벽한 독립성 검증을 보장하지 않습니다.

기본 공식 도메인 목록은 `sources.py`에 있으며 검색된 문서의 발행 주체를 판단하는 단서입니다. 미등록 산업·기업의 공식 원자료도 동일하게 심사합니다. 원문 분석과 별도 재심사 모두 해당 발행 주체의 직접 공시·발표·원자료라고 판단해야 공식 근거로 사용합니다. 단순 언론 인용은 공식 원문으로 계산하지 않습니다. 이 판정도 모델 오류 가능성이 있어 원문 링크와 인용을 함께 남깁니다. 공식 도메인 단서는 `sources.json`에 추가할 수 있습니다.

5곳 조건은 오탐을 줄이는 대신 아주 초기의 단독 보도 알림을 늦춥니다. 이를 숨기지 않고 미검증 후보는 보고서에 남깁니다. 투자수익·주가 상승을 예측하거나 시장보다 반드시 앞서 발견한다는 기능은 아닙니다.

점수는 새로운 용도 20, 수요 15, 공급 15, 가격·납기 10, 실제 자금집행·계약 20, 정책 10, 대체 10의 증거 축 합계입니다. 통계적으로 보정된 성공확률이 아닙니다.

## 실제 알림에 들어가는 내용

무엇이 달라졌는지, 어느 산업에서 어느 산업으로 수요가 옮겨가는지, 확인한 사건의 날짜, 이익을 얻을 가치사슬 위치, 공급자가 돈을 벌기 위한 조건, 반대 증거, 다음 확인 지표, 원문 링크를 보냅니다. **필요량 증가와 공급자 이익 증가를 구별합니다.** 관련 종목을 근거 없이 나열하지 않습니다.

같은 사실의 재보도는 알림 키를 유지합니다. 숫자·기간·실제 행동 변화가 있는 새 사실이나 등급 변화가 있어야 새 알림을 만듭니다. 단, 같은 사건의 표현을 모델이 다른 fact_key로 잘못 분류하는 의미 중복 가능성은 남습니다.

## 호출량과 대기열

기본 실행당 Gemini 요청은 **재시도 포함 최대 10회**입니다. 기본적으로 기사 80건씩 최대 3묶음을 검토하고, 후보 최대 3개를 원문 분석+별도 재심사합니다. 정상적으로 이 작업을 모두 수행하면 생성 요청은 최대 9회입니다. 생성 전 countTokens 사전 계수 API 요청은 별도이며, 입력량 때문에 분할할 경우 추가 계수 요청이 생깁니다. 후보당 원문은 최대 16개, 심층 검색은 최대 6개 검색어입니다.

이 수치는 전체 후보의 보유 한도가 아니라 **한 번 실행할 때 처리하는 작업량**입니다. 나머지는 다음 실행으로 넘깁니다. 대기열이 계속 늘면 `SCREEN_BATCHES`, `RESEARCH_THEMES_PER_RUN`, `MAX_GEMINI_CALLS`를 함께 늘리거나 실행 간격을 조정하세요. 피드 수집량에 비해 기본 심사량이 작을 수 있어 최초 며칠간 대기량을 확인하는 것이 필요합니다.

무료 실행을 보장하지 않습니다. Gemini API 과금은 모델·입출력 토큰·계정 조건에 따릅니다. 검색에 별도 유료 검색 API는 사용하지 않습니다. 보고서에 호출 수와 API가 반환한 토큰 통계 합계를 남깁니다. 기사 원문은 16,000자까지 로컬 보관하며 기본 모델 입력은 기사당 관련 구간 최대 3,000자입니다. PDF·동적 페이지·유료벽은 기본 구현에서 읽지 못할 수 있습니다. 원문 발췌는 비용을 줄이는 대신 중요한 문맥을 놓칠 가능성이 있습니다.

산업별 누적 수집·심사 완료·대기 건수 표를 보고서에 추가했습니다. 목록에 산업 이름만 있고 실제 기사를 못 모으는 분야가 있는지 확인할 수 있습니다.

## v2 토큰 점검 결과와 보완

v1은 실행당 호출 수만 제한했습니다. 후보당 20개 원문 × 최대 16,000자를 분석에 넣고 재심사에 다시 넣었으며, 과거 근거와 전체 가설 목록도 누적 입력했습니다. 따라서 호출이 10회 이하여도 큰 입력량이 반복될 수 있었습니다.

| 항목 | v1 | v2 기본값 |
|---|---|---|
| 심층 분석의 원문 문자량 | 후보당 최대 320,000자 | 후보당 최대 48,000자 (16개 × 3,000자) |
| 재심사 자료 | 원문 전체 다시 입력 | 인용과 그 주변 원문만 입력 |
| 과거 가설 목록 | 전체 | 현재 기사와 관련 높은 최대 40개 |
| 과거 근거 입력 | 계속 누적 | 반증·출처·증거 축을 고려한 최대 32개 |
| 동일 자료 반복 | 모델 재호출 | 자료가 같으면 7일 내 재분석 생략 |
| 생성 출력 설정 | 호출당 16,000토큰 | 탐색·분석 8,192 / 재심사 4,096 |
| 입력 사전 확인 | 없음 | countTokens API로 실제 입력 토큰 확인 |
| 봇 측 예산 | 호출 횟수 | 호출 횟수 + 실행 160,000 / 하루 500,000토큰 |

원문 문자량 상한은 85% 작아졌습니다. **전체 토큰·청구액이 85% 줄었다는 실측 결과는 아닙니다.** 토큰은 언어와 모델에 따라 달라지고 지침·스키마·메타데이터·출력·추론도 사용량에 영향을 줍니다. 원문 전체와 전체 가설·근거 기록은 계속 디스크에 남깁니다. 관련 가설 40개만 보여주는 과정에서 의미상 비슷한 옛 가설을 놓칠 수 있어 중복 판단이 완벽해지는 것은 아닙니다.

입력 계수에 실패하면 생성을 진행하지 않습니다. 입력이 호출당 36,000토큰을 넘으면 기사 묶음을 나누거나 원문 발췌 범위를 줄입니다. 그래도 기준을 넘으면 다음으로 이월하고 보고서에 제한을 남깁니다. 예산 때문에 후보를 영구 삭제하지 않습니다.

생성 직전에 입력 토큰 + 출력 한도 + 2,048토큰 여유분을 예약하고, 응답의 실제 전체 토큰 통계가 있으면 정산합니다. 응답 미확인·오류·프로세스 중단 시 예약분을 보수적으로 유지합니다. 따라서 실제 청구량보다 먼저 멈출 수 있습니다. 반대로 제공자가 반환한 실제 사용량이 예약량보다 크면 실제값을 기록하고 후속 생성을 차단합니다. **봇 내부 예산은 제공자의 절대 청구 한도 기능이 아닙니다.** 다른 프로그램·다른 data 폴더·다른 서버의 동일 API 키 사용은 합산하지 않습니다.

예산 장부 `data/usage.sqlite3`는 한국 날짜 기준으로 집계하고 재시작해도 유지됩니다. 미리보기 역시 실제 API를 사용하므로 이 장부에 기록합니다. `data/radar.sqlite3`의 미리보기 복사본과 다릅니다. 토큰 장부를 지우면 일일 예산 기억이 사라집니다.

```ini
MAX_GEMINI_CALLS=10
MAX_INPUT_TOKENS=36000
MAX_RUN_TOKENS=160000
MAX_DAY_TOKENS=500000
DOCS_PER_THEME=16
DOC_CHARS=3000
```

RSS 수집과 로컬 저장 자체는 LLM 토큰을 소비하지 않습니다. 산업 80개에 각각 AI를 호출하지 않고, 여러 산업의 기사를 같은 묶음에서 심사합니다. 따라서 산업을 늘린다고 AI 호출 상한이 자동으로 늘어나지는 않지만, 검토 대기량이 증가할 수 있습니다.

최신 기사와 오래 대기한 기사를 번갈아 심사해 신규 신호 지연을 줄이고, 산업별 순환은 유지했습니다. 새 가설과 기존 가설도 번갈아 검토하며, 원문 캐시는 7일 후 다시 가져옵니다. 새 자료가 없으면 재분석을 생략하되 7일이 지나면 재검토합니다. 같은 기사 5개로 실행을 반복한 모의 통합 테스트에서 첫 실행의 모델 호출 3회, 두 번째 실행의 모델 호출 0회를 확인했습니다. 실제 서비스의 비용 절감률은 아직 측정하지 않았습니다.

가격 확인일 2026-09-16 기준 공식 Gemini 3.8 Flash Standard 표는 2026년 말까지 입력 100만 토큰당 $0.75, 출력·추론 100만 토큰당 $3.75입니다. **예시로** 하루 입력 40만 + 출력·추론 10만 토큰이면 $0.675/일, 30일 $20.25입니다. 이것은 실측 예상 사용량이 아니며 세금·환율·모델 변경·2027년 가격 변경을 반영하지 않습니다. [공식 가격표](https://ai.google.dev/gemini-api/docs/pricing)

[토큰 계수 안내](https://ai.google.dev/gemini-api/docs/tokens), [countTokens 요청 형식](https://ai.google.dev/api/tokens), [생성 요청 형식](https://ai.google.dev/api/generate-content), [캐싱 안내](https://ai.google.dev/gemini-api/docs/caching), [UN 산업분류 범위](https://unstats.un.org/unsd/classifications/Econ/isic)를 대조했습니다. 80개 탐색 산업은 봇용 분류로 UN 분류와 일대일 대응하지 않습니다. 유료 컨텍스트 캐시는 만들지 않습니다.

추가로 남은 개발 후보는 기업 공시·무역통계·납기·가격 시계열을 직접 읽는 커넥터와 과거 사례를 이용한 탐지 시점 백테스트입니다. 이번 버전에는 해당 기능이 구현되었다고 표시하지 않았습니다. 현재는 뉴스 원문에 실린 실제 수치·행동을 근거로 삼습니다.

## 출처 추가

`sources.example.json`을 `sources.json`으로 복사한 뒤 실제 공식 도메인과 RSS/Atom 피드를 넣으세요.

```json
{
  "primary_domains": ["example-company.com"],
  "rss_feeds": [
    {"sector": "추가 산업", "url": "https://example-company.com/news.rss"}
  ]
}
```

위 주소는 형식 예시입니다. 실존 피드로 교체해야 합니다. 공식 IR·통계 원자료를 직접 정기 수집하는 커넥터는 포함되어 있지 않습니다. RSS와 후속 검색에 걸리고 읽을 수 있는 원문이 분석 범위입니다.

## 실패와 전송 이력

수집 전체 실패, 모델 호출 실패, 잘린 JSON, 잘못된 원문 인용을 정상적인 “새 신호 없음”과 구별합니다. 일부 피드·원문이 실패하면 그 제한을 보고서와 무알림 상태 메시지에 표시합니다. `SEND_EMPTY=0`으로 무알림 상태 메시지를 끌 수 있습니다.

전송 직전 내용을 outbox에 저장합니다. Telegram 성공 응답이 있는 건만 `sent`로 기록합니다. 타임아웃처럼 실제 수신 여부가 모호하면 `uncertain`으로 남기며 자동 재전송하지 않습니다. 진행 중 프로세스가 죽은 `sending`도 다음 발송 시 `uncertain`으로 바꿉니다.

```bash
python main.py --outbox
python main.py --resolve 메시지ID sent    # Telegram에서 이미 수신한 것을 직접 확인했을 때
python main.py --resolve 메시지ID retry   # 받지 못한 것을 확인하고 재전송을 원할 때
python main.py --retry-pending            # 새 분석 없이 전송 대기 건만 재전송
```

긴 알림은 메시지 크기에 맞게 나누고 조각마다 상태를 저장합니다. 일부 조각의 수신이 불명확하면 사용자의 확인이 필요합니다. 메시지 ID는 `--outbox`에 출력되는 문자열입니다.
